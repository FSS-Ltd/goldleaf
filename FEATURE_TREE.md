## Known gaps
- PORTAL-IDENTITY threat boundary: a valid Clerk session does not grant portal access. Future reads and mutations must recheck active application membership; invitations must match an authenticated verified email. Hidden sign-up controls do not restrict Clerk account creation. Auth-event audit logging and a real signed-in cross-family/revocation workflow remain required before production use. No live revocation push to an already open view exists.
- Account changes and reverification bind each operation to its originating user and session, cancel pending verification on an actor change, and clear profile forms when the actor changes. `lib/portal-session-binding.test.ts` exercises deferred retries, cancellation and actor changes; live provider account-switch verification remains untested.
- The account page reuses provider session data for `AccountIdentitySummary` before its editable forms. It displays the current name, primary email verification state and the linked Google account's own identity, with status and address in separate narrow-screen lines; `lib/account-identity-summary.test.ts` covers verified, unverified and unconnected states.
- Invitation capture reuses one exchange across React Strict Mode effect setups and only updates or navigates while mounted. The server expires the single `/invite` cookie on invalid capture and successful acceptance; generic acceptance failures retain it to allow a wrong-account user to sign in again and retry.
- PORTAL-IDENTITY graph anchors: `signinform_signinform`, `signupform_signupform`, `usesigninflow_usesigninflow`, `usesignupflow_usesignupflow`, `useprotectgate_useprotectgate`, `protect_check_resolveprotectchecks`, `protect_widget_runprotectwidget`, `ssocallback_ssocallback`, `accountprofile_accountprofile`, and `resetpasswordtask_resetpasswordtask` in [graph.json](graphify-out/graph.json).
