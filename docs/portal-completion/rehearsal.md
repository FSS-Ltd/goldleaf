# Pilot operational rehearsal and authorisation proposal

## Local synthetic evidence

On 13 November 2026, the coordinator freshly ran `bash scripts/portal-completion/local-restore-rehearsal.sh`; it exited 0 and the local log `/tmp/goldleaf-portal-restore-verification.log` ended in `PASSED`. It used an existing `postgres:17-alpine` image in a new `--network none` container with ephemeral storage, applied migrations 0001–0020, and created two synthetic families, one parent, an admin and an issued invoice. It used actual `pg_dump -Fc` and `pg_restore --exit-on-error` into a separate database. Assertions checked the family/membership relationship, allowed and denied family reads, invoice read, selected runtime grants and absence of direct family-table SELECT. It revoked schema USAGE from the synthetic runtime role, verified denied access with function EXECUTE retained, restored USAGE, verified access resumed, and compared the issued snapshot hash from source with restored post-rehearsal snapshot. The container and backup were removed by the script's exit trap. No existing environment, remote DB or provider was used.

A later 13 November run after adding local migration 0021 again passed the same script with migrations 0001–0021; the log was `/tmp/goldleaf-0021-restore.log`. It remains a synthetic local database rehearsal, not a remote migration or deployment.

This proves the selected synthetic database operations only. It does not prove a production backup is usable, all runtime grants survive, in-flight sessions are closed, or that the application itself has an entry-off switch. Native local `initdb` failed at `shmget` with `Cannot allocate memory`, including with mmap settings; Docker provided isolated local PostgreSQL without changing host kernel settings. The script requires Docker and a locally installed `postgres:17-alpine` image and never pulls one. Run from the repository root; inspect the script and image before use. It creates and stops only its own container.

On 16 November 2026, the expanded local rehearsal passed against a disposable, network-isolated PostgreSQL 17 container (`/tmp/goldleaf-16nov-restore-final.log`). It issued an unchanged 120-minute hourly legacy invoice before 0022 and a 105-minute session-fee invoice afterward, then restored both snapshots unchanged. Restored active and revoked membership generations and checked grants were verified; stale revocation failed, current revocation succeeded, and subsequent family access was denied. This is local synthetic evidence only, not production-backup or application-entry-off proof.

On 16 November, the local restore rehearsal also applied migration 0023 after preserving a pre-0022 invoice fixture. It restored a frozen synthetic alert, its original recipient path, restricted worker grants and checked that membership revocation blocks the restored alert gate. This does not test provider delivery or a production restore.

## Local authenticated portal transport

The portal can use the existing Neon HTTP and WebSocket driver against a disposable synthetic PostgreSQL database through a local Neon-compatible proxy. This is a development-only QA path; it does not bypass Clerk or portal membership checks. Use a separate Clerk development application and configure its development keys privately through the CLI. Do not use production keys, real family data, or a real Resend key. Keep local secrets outside version control and do not put them in commands, logs or this document.

Prepare a disposable database named exactly `goldleaf_auth_qa`, apply the required migrations and provision separate restricted portal runtime and event-listener roles. Set `NODE_ENV=development`, `GOLDLEAF_PORTAL_DATABASE_URL` and `GOLDLEAF_PORTAL_EVENT_DATABASE_URL` to their respective local PostgreSQL DSNs, and set `GOLDLEAF_PORTAL_LOCAL_PROXY_URL` to the proxy's loopback HTTP origin, for example `http://127.0.0.1:56778`. Both DSNs must use `localhost`, `127.0.0.1`, `[::1]` or exactly `db.localtest.me`, with no query or fragment. The proxy URL must have no credentials, path beyond `/`, query or fragment. Its `/sql` and `/v1` endpoints must support Neon HTTP transactions and WebSocket connections. Leave the flag unset outside this local setup; a configured flag in production fails closed.

The 16 November local probe used an isolated PostgreSQL container and a Neon-compatible proxy, with a loopback relay because Docker Desktop did not publish the proxy's internal-network port to the host. The relay was a private QA bootstrap and is not a repository script or a portable setup recipe. A warmed relay completed an app-equivalent query in 3.793 seconds; cold connections exceeded the earlier five-second timeout. A later local proxy response arrived 7.989 seconds after the five-second caller abort. Validated local proxy mode now permits a bounded 30-second HTTP request; the normal production deadline remains five seconds. Local HTTP single-query and batch transaction, plus a WebSocket `LISTEN` receiving a committed notification, passed. A genuine development identity signed in; authenticated role and workflow QA remains pending. The Neon HTTP endpoint setting is process-wide in local mode and rejects nonlocal database hosts, so other Neon HTTP consumers cannot use remote databases in that process.

For this local QA setup, start Next.js with hostname `localhost` and process option `NODE_OPTIONS=--dns-result-order=ipv4first`, then open `http://localhost:3000`. This is process-local; it needs no hosts-file, system DNS or repository configuration change. Binding the app to `127.0.0.1` caused a recursive self-proxy: Next normalized the URL to `localhost`, Clerk added a rewrite using that normalized host, and Next compared it against the `127.0.0.1` origin. A fresh development cache did not resolve it. With the `localhost` binding, sign-in returned HTTP 200 in 8.68 seconds initially and 2.27 seconds afterward; the public root returned 200 in 8.35 seconds, with no proxy errors observed. These timings are local startup observations, not performance acceptance.

## Remaining release rehearsal

1. Identify the exact approved environment, operator, rollback-compatible application version, intended entry-disable mechanism and affected users. There is no source-proven single portal-entry feature flag. Keep public site and issued records in scope of impact assessment. Record baseline counts, effective restricted grants, a snapshot digest and deployment identifier without copying personal data into the report.
2. Using an authorised separate isolated environment and synthetic records, capture a backup with the approved provider procedure and restore it to a distinct target. Verify parent/staff family scope, denied cross-family reads, relevant runtime grants and issued snapshot equality. Record commands, versions, target identity, timestamps, results and cleanup. Never restore over production.
3. Rehearse the chosen application-entry disable on that environment. Verify signed-out and signed-in parent, staff and admin entry, direct protected routes/actions, open views and reconnects. Confirm issued snapshots and grants remain unchanged. Re-enable and verify authorised access returns without restoring revoked access. The local schema-USAGE test above is not this application-level rehearsal.
4. Record the operator's recovery and escalation path, result and known limits. Do not modify production entry, grants, schema or records for a rehearsal without separate explicit authority. No schema rollback is implied.

## Local alert worker

The entry point `scripts/portal-alert-worker.ts` accepts only a local PostgreSQL URL in `ALERT_LOCAL_DATABASE_URL`; it uses synthetic identity and mail adapters and sends no provider mail. Run it only against a disposable migrated local database with `pnpm exec tsx scripts/portal-alert-worker.ts`. Stop with SIGINT or SIGTERM. Native integration tests require `ALERT_TEST_DATABASE_URL` pointing to a local database whose name contains `alert_test`, and fail if it is absent. The test database is populated with synthetic records; use a fresh disposable instance. The provider adapters exist in source but are not connected to this local entry point. Deployment, real identity lookup and provider delivery require separate authorisation.
