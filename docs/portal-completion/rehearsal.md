# Pilot operational rehearsal and authorisation proposal

## Local synthetic evidence

On 13 November 2026, the coordinator freshly ran `bash scripts/portal-completion/local-restore-rehearsal.sh`; it exited 0 and the local log `/tmp/goldleaf-portal-restore-verification.log` ended in `PASSED`. It used an existing `postgres:17-alpine` image in a new `--network none` container with ephemeral storage, applied migrations 0001–0020, and created two synthetic families, one parent, an admin and an issued invoice. It used actual `pg_dump -Fc` and `pg_restore --exit-on-error` into a separate database. Assertions checked the family/membership relationship, allowed and denied family reads, invoice read, selected runtime grants and absence of direct family-table SELECT. It revoked schema USAGE from the synthetic runtime role, verified denied access with function EXECUTE retained, restored USAGE, verified access resumed, and compared the issued snapshot hash from source with restored post-rehearsal snapshot. The container and backup were removed by the script's exit trap. No existing environment, remote DB or provider was used.

This proves the selected synthetic database operations only. It does not prove a production backup is usable, all runtime grants survive, in-flight sessions are closed, or that the application itself has an entry-off switch. Native local `initdb` failed at `shmget` with `Cannot allocate memory`, including with mmap settings; Docker provided isolated local PostgreSQL without changing host kernel settings. The script requires Docker and a locally installed `postgres:17-alpine` image and never pulls one. Run from the repository root; inspect the script and image before use. It creates and stops only its own container.

## Remaining release rehearsal

1. Identify the exact approved environment, operator, rollback-compatible application version, intended entry-disable mechanism and affected users. There is no source-proven single portal-entry feature flag. Keep public site and issued records in scope of impact assessment. Record baseline counts, effective restricted grants, a snapshot digest and deployment identifier without copying personal data into the report.
2. Using an authorised separate isolated environment and synthetic records, capture a backup with the approved provider procedure and restore it to a distinct target. Verify parent/staff family scope, denied cross-family reads, relevant runtime grants and issued snapshot equality. Record commands, versions, target identity, timestamps, results and cleanup. Never restore over production.
3. Rehearse the chosen application-entry disable on that environment. Verify signed-out and signed-in parent, staff and admin entry, direct protected routes/actions, open views and reconnects. Confirm issued snapshots and grants remain unchanged. Re-enable and verify authorised access returns without restoring revoked access. The local schema-USAGE test above is not this application-level rehearsal.
4. Record the operator's recovery and escalation path, result and known limits. Do not modify production entry, grants, schema or records for a rehearsal without separate explicit authority. No schema rollback is implied.

No provider or mail action is authorised by this proposal alone. The earlier single enquiry email approval is consumed. Create no real family records for testing. This is historical inventory, not permission or proof that it still exists. Explicitly approve its synthetic writes and cleanup. Preview has a working Resend key, so a synthetic family or staff invitation action may send real mail.

Proposed minimum identities: existing authorised admin plus three disposable independently authenticated users, parent A, parent B and staff. Use two synthetic families, staff assigned only A, and controlled mailboxes whose exact addresses and owners are approved. Do not use or change another person's existing account. Approve up to **six invitation emails** total (parent A, parent B, staff, and up to three resend/revocation/retry cases), and **two invoice-notification emails** to approved test parent mailboxes. Separately, approve up to **12 provider-generated verification, recovery and reverification emails**, sent only to exact approved controlled addresses, including any temporary secondary address. These are caps, not a promise all cases can be covered with those sends. Verify inbox receipt, spam and duplicates; no other recipients or unapproved sends. Invitation and invoice messages contain only synthetic data and protected links. No app-message or change-request alert emails are included without an alert-channel decision and separate approval.

Use separate sessions to test A/B isolation, staff assignment, wrong-account/replay, accepted membership revocation, open views, reconnect and direct actions. Exercise signup, verification and recovery on the three disposable identities only. Limit account changes to those users. If browser credential changes are required, hand password entry to the user; do not request or record passwords. Test expiry and delivery failure with local stubs or explicit QA controls without additional sends; do not change production clock or provider settings. Check protected invoice print and notifications with a synthetic issued invoice and simulated payment only. Capture minimal redacted evidence, send counts and outcomes. Clean up only the authorised synthetic resources, preserve required audit evidence, and report any provider data that cannot be deleted. Obtain a new decision if extra sends, accounts, real data or remote scope are needed.
