# Portal alerts: local QA proposal

**Approved for local QA only.** Scope is local QA only, using an isolated PostgreSQL database and fake Clerk/Resend adapters. No remote identity accounts, credentials, deployed worker, paid queue or production changes. Any live provider test requires separate authorisation and a private recipient handoff.

## Recipient contract

- `message.created`: active administrators, active parents of the family and active staff assigned to that family. Exclude the author's Clerk subject across all roles. Deduplicate recipient subject even when multiple memberships qualify.
- `request.created`: active administrators only, excluding the requesting subject. `request.resolved`: the original requesting parent only, if the same parent membership and generation remain active; exclude the resolving subject. Staff and other parents never see or receive private request alerts.
- Snapshot eligible membership IDs, generations and staff-assignment generations at the committed mutation; do not include later arrivals. At read and send time recheck all paths against current authority; a subject with multiple originally eligible paths may receive one alert only if at least one original path survives. Assignment deletion/reinsertion must have a fresh immutable generation. `0021` already supplies membership `access_generation`; add assignment generation in the new migration. Revoked recipients get no new submission after the authorisation boundary. Email already submitted to Resend cannot be recalled; The worker holds the surviving membership and assignment locks through a bounded provider submission and fenced finish, so a conflicting revocation or assignment removal waits for that transaction. Provider acceptance cannot be recalled.
- Email subject and body are generic, with the protected `/portal` link. No child name, message, request, resolution, secret or bearer token. The portal route rechecks identity and access. Message and request records remain authoritative independently of email delivery.

## Minimal components

1. New migration after `0021`: triggers on `portal.family_messages` INSERT and `portal.session_change_requests` INSERT / first resolution transition create durable email event and per-subject delivery rows in the same transaction. Unique event/source/subject keys handle retries and the older SQL wrappers as well as current UI calls. No direct runtime table grants; use narrowly scoped `SECURITY DEFINER` functions with safe search path and separate worker privileges. Emit content-free PG NOTIFY only as a committed wake hint. Index due jobs and enforce lease-token fencing.
2. Reuse `MessageWorkspace` family unread summaries, `Conversation` read cursors, role-filtered request contexts, `AdminRequests` and `ParentRequests`. `PortalLiveUpdates` refreshes role pages on ready/change and the server rechecks access. The existing Messages navigation has no cross-page attention indicator: the smallest addition is a badge on its existing link, derived from canonical unread counts and, for admin, open private requests. Do not add an alert inbox, acknowledgement table, separate read state or duplicate cursor. Existing parent requests show resolved status but do not record whether a resolution was seen; a durable parent resolution-unread badge cannot be derived from that status. Keep the visible resolved status and email notification; if a persistent unseen-resolution badge is explicitly required, agree on a minimal request-specific seen marker before adding state. Never expose private bodies in event payloads. Any new UI follows design-craft and applicable Stitch/Jury plan requirements.
3. Local on-demand Node worker: establish `LISTEN` before initial reconciliation, drain committed due jobs, then arm a one-shot timer for the earliest retry or lease expiry. On notify, recalculate and drain; reconnect with bounded backoff and reconcile after reconnect. No idle database/API polling. On shutdown release connections and timers. Atomic claim (`FOR UPDATE SKIP LOCKED`), bounded leases, claim tokens and fenced completion recover crashes. Worker uses injected identity and mail adapters, with real adapters reusing `lib/portal/verified-identity.ts` and `lib/portal/invoice-mail.ts` patterns. Provider submissions have timeouts and record stable key, immutable payload and first-attempt time. SQL stores the frozen generic provider payload, including the recipient address, as private data; logs contain no payload or message content.
4. Transient failures use bounded exponential due-time retries. Resend documents a 24-hour idempotency retention window (https://resend.com/changelog/idempotency-keys): retry an uncertain send with the exact same key and payload only while safely inside that window. Thereafter mark `uncertain`, surface it for manual decision, and never automatically issue a fresh key. A verified-address change cannot alter an uncertain attempt's payload. Provider acceptance is not inbox delivery.

## Local PostgreSQL connection

`pg` is not resolvable from this checkout; `@neondatabase/serverless` is installed, but its `Client` uses WebSockets and its own README says non-Neon PostgreSQL requires a WebSocket proxy. A plain local PostgreSQL 17 TCP socket therefore cannot use the existing client directly. Recommend adding `pg` plus its TypeScript types for the worker and isolated integration tests; this is a justified small dependency for the standard PostgreSQL protocol and LISTEN support. Do not implement a wire protocol or add a proxy merely to avoid it. Verify installation and native connection in implementation.

## Alternatives and verification

Recommended: local persistent Node worker, started on demand, exercises real transactional outbox and wake/retry logic with three synthetic roles and mock providers; no production bypass or external accounts. Alternative: hosted durable queue/worker later; it needs an authorised host, cost and deployment decision plus a reliable outbox relay. Neither is provisioned now. Local QA cannot establish real provider delivery or distinct real-user identity verification, and production rollout remains incomplete until an independently approved durable worker host is operating.

Tests: isolated PG commit/rollback, replay and wrapper coverage, dedupe, self-exclusion, exact private ACL, canonical unread counts and request status, revoked/removed/reassigned generation, races and claim fencing, startup/reconnect catch-up, duplicate NOTIFY, due retry timers, graceful shutdown, zero idle DB/API requests and minimal grants. Mock provider tests: verified and unverified identities, no confidential content, correct protected links, retry with stable key/payload, 24-hour ambiguity cutoff and visible manual decision. Run existing SQL/concurrency tests plus targeted unit, typecheck, lint and build checks. Confirm graph and feature tree after implementation.

## Implementation limits

Request creation snapshots the parent membership generation. Requests created before this migration have no trustworthy origin snapshot, so their resolution email fails closed. Retry attempts use a 23-hour safety cutoff and a maximum of eight claims; exhausted or uncertain work requires manual review. Migration and worker deployment require separate authorization.

The generic link deliberately uses the existing `/portal` router, which rechecks current role access. This adds a navigation step but keeps one immutable payload when a subject has multiple eligible paths. The pre-migration limitation applies only to resolution email; the underlying request can still be resolved.

The payload and key are frozen and committed before the separate gate and provider submission transaction. This preserves the idempotency record if the worker crashes while the provider call is in flight.
